# ON-28 (#125) review — integrator: changes requested

The design is sound:
- lookup tables are read from the chain, with the settled and deactivation checks;
- one Jupiter route and an allowlist of programs, with no top-level token or System instruction;
- an exact-in quote held to its request;
- balance deltas over every writable account and the hot wallet's own token accounts;
- send() signs only the transaction that passed the test run, and only once.

## Blocking: the onchain minimum of the signed transaction is never checked

checkQuote holds Jupiter's quote to our slippage. But the transaction comes separately from
POST /swap, which is the same untrusted venue, and nothing reads the minimum that the transaction
itself enforces. The test run proves that output >= minAmountOut at simulation time only. A /swap
answer whose route instruction carries slippage_bps = 10000 (or a low quoted_out_amount) passes
inspectSwap and swapEffects today. Once it lands, the Jupiter program enforces only that minimum.
Between the test run and the landing, a sandwich takes the difference, so SLIPPAGE_TOO_HIGH guards
nothing once the transaction leaves us.

Fix in inspectSwap, given the intent's amountIn and minAmountOut:
- decode the Jupiter instruction per the v6 IDL;
- accept only the exact-in route variants (route, shared_accounts_route, and their token-ledger
  forms if you allow them), and refuse every other discriminator, exact-out included;
- read the trailing args: in_amount u64, quoted_out_amount u64, slippage_bps u16,
  platform_fee_bps u8;
- require in_amount == amountIn;
- require quoted_out_amount * (10000 - slippage_bps) / 10000 >= minAmountOut;
- require platform_fee_bps == 0;
- reject with SLIPPAGE_TOO_HIGH or SIM_UNEXPECTED_EFFECT.

Add tests:
- a /swap transaction with slippage_bps 10000 is refused even though its test run is clean;
- an exact-out instruction is refused;
- a fee > 0 is refused.

## Not blocking

1. `slippage()` refuses 0 bps, while guard-core's quoteRequest allows `maxSlippageBps: 0`. Today a
   0 surfaces as a thrown Error, which becomes a 502 instead of a decision. Accept 0, or let
   guard-core clamp to 1. Tell guard-core which one you choose.
2. `checked` keeps a transaction for every intent that passed the test run but is never sent
   (shadow, owner rejected, owner timed out). That is small, but it is unbounded on a long-lived
   process. Drop entries older than a minute, or cap the map.

Shadow, Close and the approved path look right from this side: each one simulates a fresh
transaction from a fresh quote, and send() refuses anything that was not checked. I merge #125
once the blocking item lands green.
